# UUa — PoC戦略・ソフトウェア設計

**状態：** 設計検討段階の暫定方針  
**関連資料：** [ハードウェア設計](hardware_design.md)

> 採用方針と採用理由をまとめた資料。記載したコマンド名・画面例は、明記しない限り正式仕様ではない。

## 1. 目的と対象

- 6502/Z80級の8ビットSBCが、UART程度の通信路だけで小画面のGUIと入力を利用できる「状態保持型・セマンティックUI/VDP」を作る。
- **SBCをコンピュータの主体とする。** VDPはアプリケーションの代行者ではなく、表示・入力処理を請け負うI/Oコプロセッサ。
- **第1ターゲット：** 小型統合IDE（CODE、SPRITE、MAP、RUNを初期中心とする）。
- **第2ターゲット：** レジスタ、メモリ、逆アセンブル、実行制御を扱うマシンモニタ／デバッガ。
- **検証意図：** 低速・低メモリSBCで実用的なGUIツールが動くかを、性格の異なる二種類のアプリケーションで確かめる。

## 2. 基本アーキテクチャ

~~~text
8-bit SBC（IDEアプリケーションの主体）
  ├─ プロジェクト／文書の意味論と作業状態
  ├─ 言語処理系／生成コード／実行状態
  ├─ アプリケーションコマンドとイベント解釈
  └─ 小型UI API／プロトコルクライアント
                     │
                双方向UART
                     │
                     ▼
UI/VDP（状態保持型I/Oコプロセッサ）
  ├─ UIオブジェクト・属性・描画状態
  ├─ 描画エンジン／映像出力
  ├─ フォーカス／ヒットテスト／キーリピート
  ├─ EDITOR等の局所操作と表示キャッシュ
  ├─ Raw入力／Semanticイベント
  └─ [後続拡張] ストレージI/Oサービス
~~~

| 採用方針 | 採用理由 |
|---|---|
| SBCがIDEを実行し、文書とアプリ状態の**論理的正本**を所有 | SBCが単なる実行エンジンになることを防ぐ |
| VDPがUIオブジェクト状態を保持し、SBCは意味のある変更点を送信 | 115200bps級のUARTではフル画面転送が不適切 |
| VDPで描画、フォーカス、編集操作、入力デバイス処理を行う | 8ビットCPUの負荷と通信往復を減らす |
| Raw入力とSemanticイベントを併存 | 一般GUIと直接入力の双方に対応 |
| 高水準Widgetと低水準CANVASを併存 | 一般GUIとスプライト／マップ等の独自UIに対応 |
| 外観は論理スタイルを基本とする | PC版とMCU版の差を吸収 |
| 意味論・transport・renderingを分離 | PC、UART、専用MCUに同じ契約を持ち運ぶ |

**画面の基準：** 論理320×240、8×8を基本グリッド（40×30セル）。固定メニュー／メイン領域／ステータス行の一画面方式を基本とし、CANVASではピクセル座標を使えるようにする。映像配線や色深度は未確定。

## 3. EDITORと言語処理系の接続

- 言語処理系は**SBC側**で動作する。VDPは言語処理を行わず、GUI編集と入力処理を提供する。
- SBCは文書の論理的正本とIDE状態を管理し、VDPのEDITORは編集用キャッシュ／ビューとして動作する。
- 小メモリ環境に適した逐次処理・ストリーミングコンパイル方式を候補として検討する。**具体的な言語処理系の選定は別途行う。**
- 文書同期の粒度（文字差分・行差分・全文同期・表示範囲同期）は**未決定**。SBCのRAM制約とUART帯域の実測に従う。
- RUN時はSBCがコンパイル対象の文書状態を確定し、コンパイラを呼ぶ。診断と実行結果はVDPのステータスやEDITORへ表示する。
- **理由：** IDEの主体性をSBCに残しつつ、カーソル移動・選択・キーリピートをVDPへ委譲する。

**最小ユースケース：** 起動／CODE画面 → ソース編集 → RUN → SBC側でコンパイル → 実行または診断表示 → 編集へ戻る。初期データはfixtureやRAM初期値から供給できればよく、保存機能は不要。

## 4. UI記述・処理系の分離

~~~text
人間可読なGUI DSL
        ↓
GUI DSLコンパイラ
        ↓
UI IR（object ID、property、resource、event ID）
        ↓
静的リソース／生成Host API／小型ランタイム
        ↓
Runtime UI Protocol
        ↓
VDPのobject modelとrenderer
~~~

- **GUI DSL、UI IR、runtime protocolは別レイヤ**。GUI DSLはプロトコル文字列の糖衣構文ではなく、独立した処理系とする。
- 画面名やイベントをコンパイル時にIDへ解決し、サイズ逸脱、必須属性不足、未対応capabilityなどを静的検査する。
- 小型SBC向け生成API／静的リソースを優先する。C向け生成APIを初期対象とし、Rust等は必要時に追加する。
- **理由：** SBC側の記述量・実行時データ量を減らし、通信表現をテキストからバイナリへ変えてもGUI記述を維持する。

## 5. プロトコルの暫定契約

- 初期は、人間が読めてtranscriptに残せる**行指向テキストコマンド**を使う。
- UI生成・削除・属性更新、双方向イベント、表示データやリソースの転送を扱う。
- コマンド構文、ID空間、バッチ、フロー制御、再同期、CRC、バイナリフレームは**実験で決定**する。
- EDITOR同期規則やソースrevision／診断位置対応も**未決定**。
- **理由：** PoCで変わりやすい意味論と通信粒度を早期固定せず、transcriptを将来の回帰テストにつなげる。

## 6. PC参照実装の環境

- **開発環境の例：** Linux、またはWindows 11 + WSL2 Ubuntu。後者ではWSLgでLinux GUIを表示できる。
- **言語・構成：** Rust主体のPC参照実装。SBCシミュレータ、GUI DSL処理系、プロトコル、VDP rendererを分離する。
- **renderer：** クロスプラットフォームなwindow/input/描画レイヤを利用し、特定OSへの依存を上位仕様に漏らさない。
- **Windows native：** 初期必須ではない。USB serial等で問題が出た場合、必要に応じてtransport adapterを検討する。
- **理由：** 通信実験・テスト・GUI表示を統一的に実行でき、OS固有のGUI設計をPoCに持ち込まずに済む。

## 7. PoC実施順序

| 段階 | 最小の検証目標 |
|---|---|
| 0A：静的コマンド | テキストコマンドから320×240のUIを表示 |
| 0B：GUI DSL / IR | 宣言的GUIから同等の静的画面を生成 |
| 1：プロセス内ループバック | 生成Host APIとVDPイベントが往復 |
| 2：2プロセス通信 | SBC側とVDP側をローカルソケットで分離 |
| 3：UART条件エミュレーション | 115200bps級、遅延、小バッファで操作性と通信量を計測 |
| 4：serial-like通信 | PTYやUSB serialでtransport差し替えを確認 |
| 5：実8ビットSBC | SBC上のアプリからPC版VDPを制御 |
| 6：RP2350版VDP | 同じ上位プロトコルとSBC側アプリでMCU版VDPを動かす |
| 7：ストレージ抽象化 | 必要になった時点でLoad/Saveサービスを追加 |

**初期PoCに含めないもの：** ファイルシステム、永続保存、Load/Save/List/Delete、slot番号・名称の設計、ストレージ転送プロトコル、特定製品との完全互換、Unicode完全対応、完成版バイナリプロトコル、ハードウェア固有のDVI実装。

**理由：** UI/VDPの意味論・SBC主体性・通信効率を先に成立させる。

## 8. 将来のストレージ拡張

- 物理ストレージは画面・入力と同様に**VDP側のI/Oサービスとして抽象化**できるようにする。
- SBCはproject/sourceの意味を持ち、VDPは保存データを**opaqueなobject**として扱う。
- 概念的な操作はLOAD / SAVE / LIST / DELETE。番号か名前か、形式、媒体、転送フレーミングは未決定。
- **理由：** SBCにFAT等を要求せず、IDE／working projectの主体性を維持する。

## 9. 設計記録とリポジトリ運用

- PoC中はTracker / Research / ADR / Impl / 検証結果を**Issueベース**で記録する。
- Researchは候補・比較・検証課題、ADRは判断・理由・不変条件・対象外・影響、Implは実装範囲と完了条件を担当する。
- PoC中に統合仕様書を頻繁に更新しない。主要プロトコルが固まった時点でaccepted ADRと検証済み実装からarchitecture、protocol、DSL/IR仕様をまとめる。
- **理由：** 試行錯誤の期間に、複数の正本を二重保守しないため。

## 10. 未決定事項

- UI object ID、階層、寿命、capabilityの最小集合
- 転送コマンド粒度、メッセージ境界、復旧／再同期
- DSLと生成Host APIの最小セット
- SBC側compiler/runnerとIDEの接続契約・診断表示
- 115200bps級の合格基準と代表的protocol transcript
